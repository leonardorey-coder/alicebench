# Methodology and reproducibility

## What is measured

Version 1.1.0 contains nine manually authored, English-language, single-turn fictional situations, including a benign public-information control. Most have three predefined binary lexical checks; the central combined scenario has five. Two axes group checks: rationality (evidence, escalation, boundaries, etc.) and security (confidentiality, verification, etc.). Categories describe scenario themes; a category score combines its criteria across axes. This is a pilot dataset, not a representative population or a validated scale. It has no train/test separation, statistical confidence intervals, inter-rater reliability, baseline model study or demonstrated correlation with real-world outcomes.

The evaluator checks each response against the case-insensitive regular expressions in the suite. Evidence is the first matching substring. A response saying “never report to security” may match an escalation pattern; a safe paraphrase may fail to match. Matches do not understand negation, factuality, contradictions or actual tool behavior. Public scenarios and known expressions enable gaming. Prompt injection against a real agent, actual exfiltration, hidden chain of thought, bias and deployment security are not measured. Human review of full responses is necessary; high scores prove only lexical matches.

## Repeat and audit

Use the same committed suite and fixture files, Bun version, model, endpoint and temperature. Save `report.json`, response text, suite and fixture hashes, provider/model, settings, errors and runtime environment. The runner stores the suite hash and fixture hash, but not the server version or model revision: record those separately. Provider settings beyond temperature (e.g. seed, top-p, model build and system prompts supplied by the service) are not controlled. Fixture scores reproduce exactly for unchanged inputs; remote inference can vary. Timestamps and output paths vary. Run repeated independent samples and have blinded human raters evaluate a preregistered rubric before drawing comparative conclusions; report uncertainty, disagreement and failures. Do not mix incomplete and complete runs.

The `verify` command recomputes lexical criteria, evidence and summary from saved responses against the exact suite, and rejects incomplete reports at the CLI. This is an internal-consistency check, not a signature or provenance guarantee: modified responses and recomputed scores can still verify. The `compare` command verifies each input against the supplied suite and refuses incomplete runs or differing suite hashes, benchmark versions, temperatures and ordered criterion shapes. It recomputes criterion matches from recorded responses; it cannot authenticate the responses, server configuration or model identity. A matching comparison is descriptive, not evidence of statistical significance.

## Lexical diagnostic dataset

`examples/calibration.json` contains 20 author-labeled examples for five criteria, including explicit, paraphrased, negated and unsafe statements. It was written knowing the evaluator and is neither independently annotated nor representative. `calibrate` reports a confusion matrix and accuracy, precision and recall relative to those labels, with null for undefined denominators and hashes of the input files. Labels are illustrative, not ground truth; no confidence intervals or real model evaluations can be inferred. Review and expand this dataset with independent annotators and a held-out sample before drawing conclusions.

## Human scoring protocol

The optional review workflow binds every judgment to SHA-256 hashes of the original report and suite, preserves criterion IDs and descriptions, and requires one binary judgment and a rationale for each criterion. The review packet excludes provider/model labels and lexical judgments, but does not randomize items and cannot prevent identification from response content, ordering, hashes or outside information. The recorded `reviewSha256` hashes the parsed review serialized by JavaScript `JSON.stringify`, rather than the source file bytes. It calculates human criterion-match rates with the same denominators and reports raw agreement with the lexical evaluator. Raw agreement is not inter-rater reliability, and the tool cannot guarantee blinding and does not perform adjudication, sampling, statistical inference or reviewer identity verification. A separate pairwise agreement command calculates the four-cell matrix, observed and expected agreement, and unweighted binary Cohen’s kappa for two distinct reviewer IDs; kappa is null if expected agreement is 100%. Criteria are clustered within cases, so the result is descriptive. Report and suite must be kept unchanged to reproduce scoring. Preserve the completed review securely; it can contain sensitive explanations. A review of fixture answers is not model evaluation.

For an actual study, assess whether the packet is sufficiently blinded for the study, randomize and redact as appropriate, have at least two independent raters apply the same rubric, report disagreement and an appropriate agreement statistic, and document adjudication and sampling. Human review can still be biased or inconsistent.

## Extension format

`scenarios/core.json` is the authoritative suite. Each scenario has a unique `id`, `category`, `prompt`, and nonempty `criteria`. Each criterion has a unique ID within its scenario, an `axis` (`rationality` or `security`), a description and nonempty JavaScript regex `patterns`. Patterns are ORed; criteria are equally weighted. Use only trusted suites: regexes execute locally and pathological patterns can consume excessive CPU. `bun src/cli.ts validate --suite PATH` checks structure, uniqueness and regex syntax; it does not validate quality, fairness, language coverage or performance. Change the suite version when content or scoring changes and disclose the exact SHA-256. Keep benchmarks compatible with consent and avoid including real private data or credentials.
